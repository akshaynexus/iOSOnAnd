---
title: "Maintain a repo"
description: "Claim your port's repo on the tracker, prove you own it, and what you may change afterwards."
---

A repo's maintainer keeps its entry on the tracker true: the statuses of its phone, the repo's
best result, the devices it supports, what it is based on, and proof uploads. The usual way is to
hand an AI coding agent the prompt below and let it do the steps; you can also run them yourself.

## The prompt for your agent

On the site, the "Maintain a repo" button fills in the tracker URL, your repo and your phone.
The text is:

```text
I maintain an iOS-on-Android port and want to manage it on the iOSOnAnd tracker at {SITE}.
Repo: {REPO or "<OWNER/REPO>"}{, phone: DEVICE}

1. Read the tracker skill first ({SITE}/SKILL.md) and follow its rules (ask me once how tracker updates and release posts should go — auto, ask or off, saved in ~/.config/iosonand/agent-prefs.json; always ask and show the file and caption before uploading any image or video; no personal data or vendor files).
   Get the tracker CLI outside the repo (Node 18+, no install; read it and note its sha256 before running):
   mkdir -p ~/.local/share/iosonand && curl -fsSLo ~/.local/share/iosonand/cli.mjs {SITE}/cli.mjs && sha256sum ~/.local/share/iosonand/cli.mjs
   Use CLI="node ~/.local/share/iosonand/cli.mjs" with TRACKER_URL={SITE} (shown below as "node cli.mjs").
2. Sign in with my GitHub account (needs the gh CLI, logged in; gist proof only): TRACKER_URL={SITE} node cli.mjs login
3. Claim the repo: node cli.mjs repo-claim {REPO} --device {DEVICE}
   Repos under my own GitHub account are approved at once (the gist sign-in above proves the account). Only an organization's repo prints a verification code: never commit it to the main branch; push it on a throwaway branch instead: git switch --orphan iosonand-verify && printf '%s\n' '<code>' > .iosonand-verify && git add .iosonand-verify && git commit -m 'iOSOnAnd verification' && git push origin iosonand-verify && git switch -, then node cli.mjs repo-verify <claim id>, then delete the branch: git push origin --delete iosonand-verify && git branch -D iosonand-verify
4. Read the repo (README, issues, recent commits) and record what works on the phone, one area at a time:
   node cli.mjs areas
   node cli.mjs status-set {DEVICE} <area> works|in-progress|broken --detail "<what I can show>" --source "<public link>"
   Only claim what a log, capture or pushed doc shows. Ask me when unsure, and before changing a state set by hand.
5. Attach proof only after asking me (show me the exact file and caption first, even if updates are set to auto): add --photo <file> (repeatable) to the status-set or feature-add it proves, or node cli.mjs media-upload <file> --device {DEVICE} --area <area> --caption "..."
6. Check the result: node cli.mjs whoami
7. Set up tracker support and the skill (.claude/skills/iosonand-tracker/SKILL.md from {SITE}/SKILL.md) in the repo.
```

[Agent system](/docs/agents) explains what the agent does with it and the rules it follows.

## Keep the tracker updated from your repo

Once you maintain a repo, a second prompt installs the `iosonand-tracker` skill (`GET /SKILL.md`)
and sets up your coding agent to keep the tracker current according to your preferences. It runs
once in your repo: the key stays out of git (`TRACKER_TOKEN` in your shell, or the CLI's saved
login, plus `.gitignore` lines for `.env` and `cli.mjs`), the skill is saved to
`.claude/skills/iosonand-tracker/SKILL.md`, and a short Tracker section goes into the repo's agent
instructions (`AGENTS.md`, `CLAUDE.md` or `.cursorrules`). On first use, the agent asks once how
tracker updates and release posts should go (`auto`, `ask` or `off`, stored locally in
`~/.config/iosonand/agent-prefs.json`), and always asks before uploading any image or video. The
profile (My repos) and an approved claim show it filled in for your repo and phone:

```text
Add iOSOnAnd tracker support and the tracker skill to this repo ({REPO}, phone: {DEVICE}), so the tracker at {SITE} stays up to date as we make progress.

1. Install the tracker skill into the repo and read it:
   mkdir -p .claude/skills/iosonand-tracker && curl -fsSLo .claude/skills/iosonand-tracker/SKILL.md {SITE}/SKILL.md
2. Get the tracker CLI outside the repo (Node 18+; read it and note its sha256 before running):
   mkdir -p ~/.local/share/iosonand && curl -fsSLo ~/.local/share/iosonand/cli.mjs {SITE}/cli.mjs && sha256sum ~/.local/share/iosonand/cli.mjs
3. The key never goes into git. Either sign in once with my GitHub account (gh logged in, gist proof): TRACKER_URL={SITE} node ~/.local/share/iosonand/cli.mjs login
   or I make a key at {SITE}/profile/keys (scopes status:write, fork:write, media:write) and put it in my shell profile as TRACKER_TOKEN, or in a .env file that git ignores.
   Never write the key into a tracked file, a commit, a log, an issue or a PR, and never ask me to paste a token into chat.
4. Add these lines to .gitignore (create it if missing): .env, .env.*, cli.mjs, TRACKER_QUEUE.md
5. Add this section to the repo's agent instructions (AGENTS.md, or CLAUDE.md / .cursorrules if the repo uses those), so every future session follows it:

   ## iOSOnAnd tracker
   This port's per-phone status is on the iOSOnAnd tracker ({SITE}/device/{DEVICE}), repo {REPO}, phone {DEVICE}.
   Follow the iosonand-tracker skill (.claude/skills/iosonand-tracker/SKILL.md; latest at {SITE}/SKILL.md):
   - CLI: TRACKER_URL={SITE} node ~/.local/share/iosonand/cli.mjs (keep it outside the repo; read and check its sha256 when downloaded or updated)
   - first use: ask the user once how tracker updates and release posts should go (auto, ask or off) and save the answers in ~/.config/iosonand/agent-prefs.json (never committed)
   - read first: <CLI> status-get --device {DEVICE}; the area slugs: <CLI> areas
   - record after a phone boot: <CLI> status-set {DEVICE} <area> works|in-progress|broken --detail "<phone model, build, date, log line>" --source "<public commit, doc or issue URL>" --os ios|macos|tvos --version "<e.g. iOS 27.2>"
   - release updates (per posts pref): <CLI> update {DEVICE} --text "<release summary and URL>" (post-add is for Reddit links only)
   - images and videos: always ask and show the exact file and caption before any --photo, media-upload or update with files, even when updates are set to auto
   - no personal data, no vendor files, no keys in git; only claim what a log, capture or pushed doc shows; unproven stays unknown
   - tracker unreachable: <CLI> queue status-set ..., then <CLI> flush later

6. Commit only the skill file (.claude/skills/iosonand-tracker/SKILL.md), the instructions file and .gitignore. Check git status first: no key, no .env, no cli.mjs.
7. Ask me my update preferences for ~/.config/iosonand/agent-prefs.json (auto, ask or off), then read the README, issues and recent commits, compare with status-get, and propose what to sync.
```

The tracker may also offer it to you as a pull request. `scripts/tracker-prs.mjs` (run by the
admins) opens one on each claimed repo that does not have it yet. The pull request adds:

- `TRACKER.md`: the full guide, with your phone filled in;
- the same Tracker section, in each agent-instructions file your repo already has (`AGENTS.md`,
  `CLAUDE.md`, `.cursorrules` or `.github/copilot-instructions.md`), or in a new `AGENTS.md`;
- a Claude Code skill, `.claude/skills/iosonand-tracker/SKILL.md`;
- the `.gitignore` lines.

It changes no code and holds no key; merge it, edit it or close it as you like. A repo that already
has `TRACKER.md` or the skill, or an open pull request from the tracker, is skipped.

## The flow

On the site, a phone nobody maintains shows **Add your repo** next to its name, and each of its
unclaimed repos (under "Supported by" and in a "Nobody maintains this phone yet" card) has a
**Claim** button. When you are signed in and a tracked repo is under your GitHub login and
unclaimed, the phone's page and the Overview show it first ("This is your repo", "You have repos
to claim"). The claim dialog's agent prompt claims the repo and then sets up tracker support in it
(the section below), so the page stays current. From the CLI:

1. **Sign in.** `node cli.mjs login` proves your GitHub account with a secret gist (the `gh` CLI
   must be logged in); the CLI deletes the gist afterwards. Your tracker account is now bound to
   that GitHub login.
2. **Claim.** `node cli.mjs repo-claim OWNER/REPO --device <slug>` sends
   `POST /api/repos/claim`. The repo may be given as `OWNER/REPO` or a github.com URL.
   - The tracker does not list the repo yet: `--device` is required; the claim adds the repo as a
     fork of that phone (`fork-claim`). `repo-add OWNER/REPO --device <slug> --branch main
     --best-result "..."` does the same with the repo's branch and best result.
   - Another user maintains the repo: 409, and the hint names them. They (or an admin) can step
     down with `repo-unmaintain`.
3. **Owner check or proof file** (below). A repo is claimed by its owner: the claim needs a
   linked GitHub account, and that login must be the repo's owner (or, for an organization's
   repo, one of its members).
4. **Work.** `whoami` lists the repo under `maintains_repos` and its phone under `maintains`.

## Several maintainers

A repo can have any number of maintainers: people working on one port together (OneiOS has
several). Each of them maintains the repo and all its phones, and none of them takes it from the
others. Ways in:

- **The repo's GitHub owner** claims it and is approved at once, also when others maintain it
  already.
- **A contributor** (GitHub lists commits by your login in the repo) claims it: the claim waits for
  a yes from one of the repo's maintainers, or an admin. They see it on their profile (Claims, Repo
  claims to review; admins: the Admin tab) or with `node cli.mjs repo-claims`, and answer with `repo-claim-approve <id>` or
  `repo-claim-reject <id>`. The claim lasts 30 days.
- **A maintainer adds you** by your GitHub login: profile, My repos, Add a maintainer, or
  `node cli.mjs repo-maintainer-add OWNER/REPO --github LOGIN`. You need an account linked to that
  login (sign in with GitHub) first.

`node cli.mjs repo-maintainers OWNER/REPO` lists them. Anyone steps down with `repo-unmaintain
OWNER/REPO`; removing someone else (`repo-maintainer-remove OWNER/REPO --github LOGIN`) takes the
repo's GitHub owner or an admin.

## The two checks

| Check | When | What the tracker does |
|---|---|---|
| owner | your GitHub login (proven at sign-in) equals the repo's `OWNER`, case-insensitive | approves at once: 200, method `owner` |
| proof file | `OWNER` is a GitHub organization, and your GitHub login is a public member of it or a contributor to the repo | 202 with a pending claim and a code; you prove push access with a file |
| review | `OWNER` is another person's login and yours has commits in the repo | 202 with a pending claim (no code); a maintainer of the repo or an admin approves it |
| refused | no GitHub account linked, or another person's repo you have no commits in | 403; the hint says why. A maintainer can add you by your GitHub login |

The proof file goes on a throwaway branch, so nothing lands on your main branch or its history:

```sh
node cli.mjs repo-claim OrgName/port --device s25        # prints claim #17 and its code
git switch --orphan iosonand-verify                      # an empty branch of its own
printf '%s\n' 'iosonand-verify-...' > .iosonand-verify    # the code alone
git add .iosonand-verify && git commit -m "iOSOnAnd verification"
git push origin iosonand-verify && git switch -
node cli.mjs repo-verify 17                              # POST /api/repos/claim/17/verify
git push origin --delete iosonand-verify && git branch -D iosonand-verify
```

The code is single-use and only proves push access for that one claim; it is not a secret. A repo
under your own GitHub login needs no code at all: sign in with `node cli.mjs login` (a gist proves
the account) and the claim is approved at once.

`repo-verify` reads `.iosonand-verify` from the default branch (`https://raw.githubusercontent.com/OWNER/REPO/HEAD/.iosonand-verify`,
then the GitHub contents API) and from the `iosonand-verify` branch
(raw.githubusercontent.com caches for up to five minutes). The trimmed content must equal the
code. A claim lasts 24 hours; asking again within that time returns the same claim and code.

| Answer | Meaning |
|---|---|
| 200 | approved: you maintain the repo and its phone |
| 403 | your GitHub login is neither a public member of the organization nor a contributor to the repo: make your membership public on `github.com/orgs/OWNER/people`, then verify again |
| 422 | `verification file not found or wrong`: the hint says which |
| 410 | the claim expired: run `repo-claim` again for a new code |
| 409 | the claim is not pending any more (approved, rejected), or someone else got the repo first |
| 502 | GitHub could not be reached; retry |

An admin can also approve a pending claim without the file (`repo-claim-approve <id>`, method
`admin`) or reject it (`repo-claim-reject <id>`). A rejected or expired claim that had added a new
repo removes that repo again, unless someone maintains it.

## What a maintainer may do

After approval you are the repo's maintainer (`forks.maintainer_user_id`) and a maintainer of its
phones. One claim covers every phone the repo runs on; there is no claim per phone:

- **Its own phone, and the phones an admin lists on it** (`primary`, `merged`, `ported`): you
  maintain them as long as you maintain the repo. A phone an admin adds later is yours at once.
- **A phone you add yourself**: on your profile (Overview tab, My repos, Add a phone), with
  `repo-support OWNER/REPO <phone> --support claimed`, or with `repo-claim OWNER/REPO --device
  <phone>` for a repo you already maintain. You maintain it at once when nobody else does; when
  another user maintains it, a device claim waits for an admin, so adding a phone to your repo
  never takes it from its maintainer. Removing the phone from the repo ends it.
- **A new repo for a phone already listed**: "Add your repo" on the phone's page, or
  `repo-claim OWNER/REPO --device <phone>`.
- **A phone the tracker does not list**: in "Add your repo", choose "My phone isn't listed" and
  give its name (codename and chip are optional), or send `new_device: {name, model, soc}` to
  `POST /api/repos/claim`. Only with a repo your GitHub login owns, since that claim is approved at
  once; the phone starts with every area unknown. 409 when the phone is listed already (the hint
  names it).

One account can maintain any number of repos and phones this way.

You may:

- set the phone's statuses (`status-set`), except the three OneiOS-only areas on a phone whose
  port is not OneiOS-based (400 `area not applicable`);
- update the phone's fields, such as `best_result` and `ios_version` (PATCH /api/devices/slug);
  its photo and `base` are admin-only;
- update the repo (`fork-sync`, PATCH /api/forks/id): branch, URL, best result, ported,
  fork-only, notes; `verified` stays `fork-claim` (only an admin sets `reproduced` or `merged`);
- record what the repo is based on (`repo-lineage`) and that it supports another phone as
  `claimed` (`repo-support ... --support claimed`); `merged`, `ported` and `primary` are admin-only;
- upload screenshots and clips for the phone (`media-upload`) and delete your own uploads;
- add Reddit posts (`post-add`), like any maintainer;
- create API keys for your agents with only the scopes they need ([API keys](/docs/api-keys)).

To step down: `node cli.mjs repo-unmaintain OWNER/REPO` (`DELETE /api/forks/id/maintainer`). The
phones you maintained through the repo go too, unless you maintain them some other way (another
repo, or your own device claim).
