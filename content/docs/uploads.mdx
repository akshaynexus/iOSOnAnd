A maintainer attaches proof to a phone: a screenshot of a working area, a clip of the boot. Files
are stored in object storage; the database keeps one
`media` row per file.

## Upload

```sh
node cli.mjs media-upload boot.mp4 --device s25 --area boot --caption "cold boot to the lock screen"
node cli.mjs media-list --device s25
node cli.mjs media-delete 14
```

`media-upload` sends `POST /api/media` as `multipart/form-data` with the fields `device`
(required), `fork_id`, `area`, `history_id`, `feature_id`, `caption` and then `file`. With curl:

```sh
curl -H "authorization: Bearer $TOKEN" -F device=s25 -F area=wifi -F caption="joined WPA2" -F file=@wifi.png "$BASE/api/media"
```

- Who: an admin, or a maintainer of the device. A key needs `media:write`.
- The text fields must come **before** the file part: the server checks the device and your rights
  before it stores anything. `?device=` in the URL works too.
- From the site (session cookie) the page sends the header `X-Requested-With: iosonand`, because
  the body is not JSON ([API conventions](/docs/api#conventions)).
- The answer is 201 with the media row; the file is at its `url`.

## Link a photo to what it proves

A photo or clip can be linked to a status change (the write that set an area) or to a
[notable feature](/docs/data-model#device_features). The phone's "What changed" timeline and its
features list show the linked files next to the change or feature.

```sh
# write a status and attach its proof in one go (repeat --photo, up to 10 files)
node cli.mjs status-set s25 wifi works --detail "joins WPA2, 80 Mbit/s" --source "<commit>" --photo wifi.png
# the same for a feature
node cli.mjs feature-add s25 "IR blaster" works --detail "..." --source "<log>" --photo ir.mp4
node cli.mjs feature-set s25 7 --photo ir2.jpg
# link an upload afterwards, or unlink it with none
node cli.mjs media-link 14 --history 812
node cli.mjs media-link 14 --feature 7
node cli.mjs media-link 14 --history none
```

- A status write answers with `history_id`, the change it added. Send it as `history_id` in the
  upload; the upload's area becomes the change's (another `area` is 400).
- `feature_id` links a notable feature. Both must belong to the upload's phone (404 otherwise).
- `PATCH /api/media/{id}` with `{"history_id": N}`, `{"feature_id": N}` (null unlinks) or
  `{"caption": "..."}` links or captions an existing upload: the uploader, an admin or a maintainer
  of the phone.
- `GET /api/devices/{slug}/history` and the feature lists carry each row's `media`;
  `GET /api/media?history_id=` and `?feature_id=` list them too.
- Removing a feature clears the link; the upload stays on the phone.

## Types and sizes

The type comes from the file's first bytes, never from its name or the client's Content-Type.

| Kind | Types | Limit |
|---|---|---|
| image | `image/jpeg`, `image/png`, `image/webp`, `image/avif` | 15 MB |
| video | `video/mp4`, `video/webm`, `video/quicktime` | 95 MB |

| Answer | Why |
|---|---|
| 411 | no `Content-Length` |
| 413 | `Content-Length` over 95 MB (refused before the body is read), or an image over 15 MB |
| 415 | not `multipart/form-data`, or a file that is none of the types above (GIF, SVG, HEIC, PDF ...) |
| 400 | no file, no device, a second file, a caption over 500 characters |
| 403 / 404 | not a maintainer of the device / unknown device, area or fork |

Image width and height are read from the file (PNG, JPEG, WebP, AVIF headers); videos have none.

## Storage and serving

- The body is streamed: files up to 8 MiB go to R2 in one put, larger ones as an R2 multipart
  upload of 8 MiB parts, so a 95 MB clip is never held in memory whole. A refused or failed upload
  is aborted, so nothing is left behind.
- Keys look like `s25/2026-11-23-<random>.mp4`.
- `GET /media/<key>` (not under `/api`) streams the file with its type,
  `Cache-Control: public, max-age=31536000, immutable`, an ETag (304 on `If-None-Match`),
  `X-Content-Type-Options: nosniff` and a sandboxing Content-Security-Policy.
- It supports `Range: bytes=a-b`, `bytes=a-` and `bytes=-n` (206 with `Content-Range`, for video
  seeking); a range past the end is 416.

## List and delete

- `GET /api/media?device=&fork_id=&area=&kind=image|video&limit=&offset=` (public), newest first.
  Each item: `id, device_slug, fork_id, area_slug, url, content_type, kind, bytes, width, height,
  caption, user, created`.
- Every device carries `latest_media` (its newest image) and `media_count`.
- `DELETE /api/media/{id}`: the uploader or an admin. It is a soft delete (the row keeps
  `deleted = 1`) and the R2 object is removed, so `/media/<key>` answers 404 afterwards.

## Photo updates

An update is a maintainer's post on a phone: what changed, with up to 10 photos or clips. It shows
in the Updates section of the phone's page (newest first); its files also show in the gallery.

```sh
node cli.mjs update s25 boot.mp4 wifi.png --text "Wi-Fi joins networks now; Safari loads pages" --area wifi
node cli.mjs updates s25
```

`update` uploads each file (`POST /api/media`, captioned with the text), then posts them together:
`POST /api/devices/{slug}/updates {body, media_ids}`. On the phone's page, maintainers post the
same from the Updates form (images lose their EXIF data first, as with any upload).

- Who: admin, or a maintainer of the phone; a key needs `media:write`.
- `media_ids`: your uploads of that phone that are in no other update (else 400).
- `GET /api/devices/{slug}/updates` (public) lists them with their media;
  `DELETE /api/devices/{slug}/updates/{id}` (the author or an admin) removes one and leaves its
  files in the gallery.

An update is a claim like any other: it shows what the maintainer saw. A status change still goes
through `status-set` with its detail and source.
