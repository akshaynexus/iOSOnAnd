The database is D1 (SQLite). `migrations/` is the source of truth; `schema.sql` is a reference
dump of the schema after all migrations. A schema change is a new `migrations/NNNN_name.sql`.

## devices

One row per phone.

| Column | What |
|---|---|
| `slug` | primary key, lowercase letters, digits and dashes, e.g. `s24-ultra` |
| `name`, `model`, `soc` | `Galaxy S24 Ultra`, `SM-S928`, `SM8650` |
| `gpu` | the GPU when a maintainer or an admin names it, e.g. `Adreno 750`; empty means it comes from the chip (migration 0017) |
| `repo_kind` | `home`, `fork`, `snapshot`, `mirror` or `none` |
| `status` | the headline state, one of the four states below |
| `best_result` | the furthest the port got, in one line |
| `ios_version` | the iOS (or iPadOS, tvOS) version the port runs, as its source states it, e.g. `iOS 16.7.16`, `iOS 27.0.1 (24A446)`; empty when not stated |
| `macos_version` | the macOS version a port runs on the phone, as its source states it, e.g. `macOS 27.2`; empty when none (migration 0011) |
| `tvos_version` | the tvOS version a port runs on the phone; empty when none (migration 0012) |
| `base` | `oneios` (a OneiOS-based port: hosted XNU next to Android) or `other`. Used only for the not-applicable rule below |
| `image_url`, `image_credit`, `image_license`, `image_source_url` | a photo of the phone: the image, its author, its licence, and the page it comes from. Set by an admin (`device-set`) |
| `notes`, `updated` | free text; date of the last write |

Every device response also carries, computed:

- `supported_by`: every repo that supports the phone (from `repo_devices`), upstream repos first.
- `families` and `family`: the `base_project` labels of those repos (and of the phone's own
  forks), ordered by the best support level (primary, merged, ported, claimed), then by how many
  repos carry it. `family` is the first one, or empty when the phone has no repo; `unknown` only
  when no repo of the phone has a known family. `GET /api/devices?family=` filters on it.
- `latest_media` (its newest image) and `media_count`.
- `gpu`, `gpu_source`, `gpu_family` and `gpu_driver`: the GPU (the device's own `gpu`, else
  looked up from the chip, `gpu_source` says which; empty when the chip is not known), its family
  (`Adreno 6xx`, `Mali Bifrost`, `Mali Valhall (JM)`, `Mali Valhall (CSF)`, `PowerVR Rogue`,
  `Xclipse (AMD RDNA)` ...) and the open driver whose code is the hardware reference for that family
  (freedreno / Turnip, Lima, Panfrost, Panthor, Mesa powervr). `GET /api/devices?gpu=` filters on
  the GPU or its family: `Adreno 619`, `Adreno 6xx`, `Mali-G57`, `Mali Valhall`.

## areas

The checklist: 28 areas, the same for every device (`metal` and `gles`, Metal and OpenGL ES acceleration, from migration 0013; `mobile-data` and `hotspot`, cellular data and Personal Hotspot, from migration 0016). `src/lib/areas.ts` groups them into
categories for the Compatibility tab and the device page.

| Category | Area slugs |
|---|---|
| Boot and system | `boot`, `return-to-oneui`, `stability`, `ipc`, `kernel-mem` |
| Display and GPU | `gpu`, `metal`, `gles`, `brightness` |
| Input | `touch`, `keyboard`, `haptics`, `sensors` |
| Audio and media | `audio`, `camera`, `video-encode` |
| Connectivity | `wifi`, `bluetooth`, `modem`, `mobile-data`, `hotspot`, `calls`, `sms` |
| Power and thermal | `battery`, `thermal` |
| Security and apps | `passcode`, `face-id`, `wallet` |

`scope` is `all`, `oneios` or `extra`. `return-to-oneui`, `ipc` and `kernel-mem` are `oneios`: they describe
OneiOS's hosted design (switching back to One UI, host-call IPIs, the hosted kernel's memory).
For a device whose `base` is not `oneios` they are **not applicable**: a write is 400
`area not applicable`, and the site shows N/A and leaves them out of the unknown counts.

`extra` is for an area outside the iOS checklist: writable on every phone, not counted in its
"N of M areas work". (Migration 0011 added a `macos` area of this kind; 0012 replaced it with
statuses per system, below.)

## device_status

One row per device, area and system: `state`, `detail` (what was seen), `source` (the file, log,
commit or link that proves it), `os` and `os_version`. The primary key is
`(device_slug, area_slug, os)`; a write replaces the row.

`os` is the system the row is about (migration 0012): `ios` (iOS and iPadOS, the default and the
checklist the site counts), `macos` or `tvos`. A phone can have Wi-Fi working on iOS and broken on
macOS. `os_version` is the version the evidence was seen on (`iOS 27.2`, `macOS 27.2`); a write
that states one also sets the phone's `ios_version`, `macos_version` or `tvos_version` when that
is empty or names an older version (`iOS 27.2` replaces `iOS 16.5`, not the other way round). `GET /api/devices/{slug}` returns the iOS rows as `statuses`, as before, and the
others as `os_statuses` by system. `GET /api/status` takes `?os=` (`ios` by default, or `all`). On
the phone's page the area table switches between the systems; the grid's **macOS** filter shows
the phones where macOS boots or is under way, or that state a `macos_version`.

```sh
node cli.mjs status-set <device> wifi works --os macos --version "macOS 27.2" --detail "..." --source "..."
node cli.mjs status-get --device <device> --os all
```

## gpu_accel

How a phone's GPU acceleration works and how fast (migration 0018), one row per phone, written by
its maintainers or an admin (a key needs `status:write`):

| Column | What |
|---|---|
| `method` | `native-metal` (a native Metal driver), `metal-vulkan` (Metal translated to Vulkan: metal2vulkan on Turnip or PanVK), `metal-gl` (Metal over OpenGL), `gles` (OpenGL ES only), `virtio-gpu` (forwarded to Android's GPU from a hosted guest, e.g. OneiOS), `cpu` (software rendering), `other`, `unknown` |
| `stack` | the chain of components, e.g. `AdrenoMetal -> metal2vulkan -> Turnip -> Adreno740 kernel driver` |
| `fps_low`, `fps_high`, `fps_note` | the measured frame rate (a range, or one number in `fps_low`) and what was measured |
| `repos` | the code that does it, `OWNER/REPO` |
| `detail`, `source`, `os_version`, `who`, `updated` | as on a status row |

It shows under "GPU acceleration" on the phone's page (with the GPU, its family and the open
driver), as `gpu_accel` on the device, at `GET /api/devices/{slug}/gpu`, and in `references`.

```sh
node cli.mjs gpu-get <device>
node cli.mjs gpu-set <device> --method metal-vulkan --stack "AdrenoMetal -> metal2vulkan -> Turnip" \
  --fps 40-58 --fps-note "idle lock screen" --repos UniXNU/AdrenoMetal --source "<link>"
```

## porting_records and porting_components

Porting records and driver components imported from a porting framework (migration 0019): UniXNU's
device records and `components.toml`, the data behind unixnu.com/devices. A record is one port repo:
its codename, SoC, OS profile, summary, and for each area (cpu, memory, storage, display, input, gpu,
network, audio, bluetooth, cellular, power ...) a status (`device-verified`, `host-verified`,
`implemented`, `planned`, `not-applicable`), the components it uses, what it achieved, its limits, the
next step, the build and boot commands and the first evidence. A component is a driver or tool with the
hardware it drives, its repository and build stage; `used_by` lists the records that use it with that
area's status. Read by everyone, written by an admin import.

```sh
node cli.mjs porting <device>                          # its repos' records, best-verified first
node cli.mjs porting --component Ath12kWifi            # every board using that driver
node cli.mjs porting --area gpu --status device-verified
node cli.mjs porting-get uke-nsr-xine                  # one record in full
node cli.mjs components wifi                           # drivers matching "wifi", with their boards
```

Device responses carry `porting` (the record summaries of the phone's repos), and the phone's page
shows them under "Porting records".

## gpu_issues

Known GPU issues per phone (migration 0020), so a porter with the same symptom finds the cause and the
fix: `kind` (`white-widgets`: HEIC snapshots fail without a hardware HEVC encoder; `black-ui`: black
widgets, blurs, materials or lock screen from a failing Metal path; `gpu-fault`, `out-of-memory`,
`artifacts`, `slow`, `crash`, `other`), `state` (`open`, `workaround`, `fixed`), `title` (the symptom),
`cause`, `fix`, `detail`, `source`, `os_version`, and who changed it last. The phone's maintainers (or
an admin) write them; a key needs `status:write`. They show in the phone's "GPU acceleration" card and
as `gpu_issues` on the device.

```sh
node cli.mjs gpu-issue-add <device> "White widgets" --kind white-widgets --cause "no hardware HEVC encoder" --source "<log>"
node cli.mjs gpu-issue-set <device> <id> --state fixed --fix "paravirtualized VideoToolbox encoder" --source "<commit>"
node cli.mjs gpu-issues --kind white-widgets          # every phone that hit it, with the cause and fix
```

API: `GET/POST /api/devices/{slug}/gpu/issues`, `PATCH/DELETE /api/devices/{slug}/gpu/issues/{id}`,
`GET /api/gpu/issues?kind=&state=&q=`.

## stats_daily

Public usage statistics (migration 0021): `day`, `kind`, `key` and a count `n`, nothing per person.
`device_view` (key: phone slug) and `profile_view` (key: user id) count page opens, once per browser
and day; `search` (key: the search, lowercased) and `search_device` (key: the phone it matched best)
count searches that match a phone. The site sends them with `POST /api/stats/hit`; `GET /api/stats`
and the [Statistics](/stats) page read them, and device and profile responses carry `views`
(`d7`, `d30`, `total`).

## device_features

Other notable features of a phone (migration 0014): what the checklist does not list, or uncommon
hardware that works (an IR blaster, a stylus, a second screen, a hinge sensor). Each row has a
`name`, the system it is on (`os`), a `state`, `detail` and `source` like a status row, and who
changed it last. The phone's maintainers (or an admin) write them; a key needs `status:write`.
They show under "Other notable features" on the phone's page and as `features` on the device.

```sh
node cli.mjs features <device>
node cli.mjs feature-add <device> "IR blaster" works --detail "what you saw" --source "log or video"
node cli.mjs feature-set <device> <id> --state broken --detail "..."
node cli.mjs feature-remove <device> <id>
```

## status_history

One row per status write (migration 0012): the device, area, system and version, the state
before (`old_state`, null when there was no row) and after, the detail and source, who and when.
`GET /api/devices/{slug}/history` (CLI `history <device>`) lists them newest first; the phone's
page shows them under "What changed", grouped by who and time, with the maintainers' posted
updates. Changes from before the table existed were read back from the changelog, without the
state before or the source.

| State | Meaning |
|---|---|
| `works` | works on that phone, with a source |
| `in-progress` | partly works, or a fix is being proven |
| `broken` | tried and fails |
| `unknown` | nothing proven; an area with no row counts as unknown |

## forks (repos)

Every tracked GitHub repo. The repo name is unique (case-insensitive).

| Column | What |
|---|---|
| `repo`, `branch`, `url` | `OWNER/NAME` on GitHub; `branch` may list several, comma-separated (the first is where the repo link goes); the URL defaults to `https://github.com/<repo>` |
| `kind` | `upstream` (a project's main repo: akshaynexus/OneiOS), `standalone` (an own port that is no fork, e.g. akshaynexus/iOSPlus10, xaxaapple/s25ver) or `fork` |
| `device_slug` | the repo's primary device (may be null) |
| `best_result` | the repo's own claim |
| `ported`, `fork_only` | what already flowed back to OneiOS `main`; what is still only in the repo |
| `verified` | `fork-claim`, `reproduced` or `merged` |
| `maintainer_user_id`, `maintainer_since` | the first of its maintainers, kept for older clients; `repo_maintainers` has them all |
| `base_project` | the family label: `OneiOS`, `ios-sweet`, `HackiOS`, `UniXNU`, `Scion`, `iOSPlus10`, `Jesvi-iOS`, `Open Mapple`, `xnu-hd2`, `custom`, `emulator`, `tooling`, `unknown` |

`verified` is a trust statement: `fork-claim` (the repo says so; every repo starts here, and a
maintainer can only file this), `reproduced` (reproduced on hardware, set by an admin), `merged`
(the code is in OneiOS `main`, set by an admin).

### repo_devices: the phones a repo supports

One row per repo and device: `support` and, for work that came from another repo, `via_fork_id`.

| support | Meaning |
|---|---|
| `primary` | the repo's own phone (akshaynexus/OneiOS: s24-ultra) |
| `merged` | fork work merged into the repo (OneiOS: s25 via xaxaapple/s25ver, s26-ultra via YMGPwcca/OneiOS) |
| `ported` | fork work ported into the repo (OneiOS: s25-ultra via YumikoHayamato/OneiOS, a56 via Musicalista/OneiOS-A56) |
| `claimed` | the repo says it supports the phone (every fork's own device) |

The `note` says what was taken, when, and what was not taken. Fork responses carry this as
`supports`; device responses as `supported_by`. Admins add `primary`, `merged` and `ported` rows,
a repo's maintainer `claimed` ones (`repo-support`).

### repo_lineage: what a repo is based on

One row per (repo, base, relation). `base` is `OWNER/REPO` or a project name; `fork_id` and
`base_fork_id` are set when the repo or the base is tracked. Rows also describe untracked repos
(the parents and bases of tracked ones), so the family tree stays connected; `lineage_repos` holds
their family label.

| relation | Meaning |
|---|---|
| `fork-of` | the GitHub fork parent (or the root of the fork network) |
| `derived-from` | copied from or based on, per the README |
| `ported-from` | parts ported in |
| `uses` | a kernel, loader or tool it builds on |

Fork responses carry `based_on: [{base, base_repo_url, relation, note}]` (no URL when GitHub has
no such repo). `GET /api/lineage` returns the whole graph: nodes (tracked and untracked repos)
and edges from a repo to its bases. The data comes from the GitHub API (fork parents and READMEs);
maintainers add rows with `repo-lineage`.

The Repos tab's "By base" view groups repos with this data. Each fork goes under the main or
standalone repo at the root of its `fork-of`, `derived-from` or `ported-from` chain (`uses` is
not a parent), with forks of forks indented under their parent. A fork whose base is not tracked
goes under that base's name, and a repo that records no base goes under "Base not recorded".

## repo_maintainers

Everyone who maintains a repo: `fork_id`, `user_id`, `since`, `added_by`. A repo can have several
(collaborators on one port); each maintains the repo and its phones. The API shows them as
`maintainers` on every repo. See [Maintain a repo](/docs/maintain-a-repo#several-maintainers).

## claims and repo_claims

- `claims`: who maintains which device: `pending`, `approved` or `rejected`. An approved claim
  makes its user a maintainer of the device.
- `repo_claims`: a claim on a repo: `method` (`owner`, `proof-file`, `admin`), `nonce` (the
  verification code), `status` (`pending`, `approved`, `rejected`, `expired`; 24 hours),
  `fork_created` (the claim added the repo) and `device_claim_id` (the device claim the approval
  granted). See [Maintain a repo](/docs/maintain-a-repo).

## media

Uploads on R2: `device_slug`, optional `fork_id` and `area_slug`, optional `history_id` (the
status change it is evidence for) and `feature_id` (the notable feature it shows), `user_id`, `r2_key`,
`content_type` (from the file bytes), `bytes`, `width`, `height`, `caption`, `created` and
`deleted` (a soft delete; the R2 object is removed). See [Uploads](/docs/uploads).

## device_updates

A maintainer's post on a phone: `device_slug`, `user_id`, `body` (up to 2000 characters),
`created` and `deleted`. Its photos and clips are `media` rows with `update_id` set. See
[Uploads](/docs/uploads#photo-updates).

## device_catalog

Every Android phone and tablet Google Play lists (`play_public/supported_devices.csv`), one row
per brand and marketing name: `brand`, `name`, `codenames`, `models` and a lowercased `search`
column. Not tracker data: it is what `GET /api/catalog?q=` and the "My phone isn't listed" picker
search when someone adds a phone (TVs, boxes, car units and watches are left out).

## reddit_posts

Links shown on the Updates tab: `title`, `url` (unique, stored as `https://www.reddit.com/r/...`
without a query), `published` (`YYYY-MM-DD`), `note`, and a thumbnail from the post: `image_url`,
`image_width`, `image_height`. See [Data sources](/docs/sources).

## changelog

Every write adds a row: `who` (`@github_login`, the display name, or `user#id`), `summary`
(for example `status s24-ultra/wifi -> in-progress: ...`) and `created`.

## Accounts

`users`, `sessions` (cookie logins), `api_tokens` (tokens and API keys, stored as SHA-256 hashes,
with `scopes`, `expires` and `last_used`), `password_resets` (reset links, stored as SHA-256 hashes,
30 minutes, one use), `login_challenges` (gist-proof nonces, 10 minutes, one
use). See [Permissions](/docs/permissions) and [API keys](/docs/api-keys).

## Where the data comes from

The starting data came from these sources (see also [Data sources](/docs/sources)):

- **OneiOS's own docs** (README, `docs/forks.md` and the device records) for the S24 Ultra and the
  phones supported through ported or merged fork work. Rows whose detail ends with
  `(OneiOS maintainer, date)` come from the project's maintainer and are authoritative.
- **r/hackios threads** for other devices. Each such status row has `detail` starting with
  `reddit claim (YYYY-MM-DD):` and `source` set to the thread's permalink.
- **The GitHub API** (repo metadata, fork parents and READMEs, no clones) for lineage and
  `base_project`.
- **`ios_version`** from what each device's best result, status details or notes state; empty
  when they state none.
- **Photos** set by an admin, credited with author and licence and linked to
  their source page.

After the seed, rows change through the API; the changelog records each write. Two sync scripts
write through it too, and never change a maintainer's row:

- **The HakiOS ports registry**:
  detail starts with `HakiOS registry:`, source the port's registry page.
- **hackiosx.dev**: detail starts
  with `hackiosx.dev`, source the section of its projects page.
