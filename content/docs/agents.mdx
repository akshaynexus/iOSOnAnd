The tracker is built to be written by agents. A port's maintainer hands an AI coding agent one
prompt; the agent downloads the CLI, signs in, claims the repo, reads the repo and records what
works, one area at a time, with a source for each claim. This page is that system end to end.

## The pieces

| Piece | What it is |
|---|---|
| The prompt | the text the maintainer gives the agent (below; the site's "Maintain a repo" button fills it in) |
| `cli.mjs` | the agent's tool surface: one file, Node 18 or newer, no install, `GET /cli.mjs` serves it |
| Auth | a GitHub gist-proof login, or an API key with scopes in `TRACKER_TOKEN` |
| Repo claim | makes the agent's user the maintainer of the repo and its phone |
| The rules | what an agent may claim, and what it must never overwrite |
| [`SKILL.md`](/SKILL.md) | the same flow and rules as a drop-in skill file (`GET /SKILL.md` serves it alongside `GET /cli.mjs`) |

## The prompt

The site shows this text with the tracker URL, the repo and the phone filled in
([Maintain a repo](/docs/maintain-a-repo) explains each step):

```text
I maintain an iOS-on-Android port and want to manage it on the iOSOnAnd tracker at {SITE}.
Repo: {REPO or "<OWNER/REPO>"}{, phone: DEVICE}

1. Read the tracker skill first ({SITE}/SKILL.md) and follow its rules (ask me once how tracker updates and release posts should go — auto, ask or off, saved in ~/.config/iosonand/agent-prefs.json; always ask and show the file and caption before uploading any image or video; no personal data or vendor files).
   Get the tracker CLI outside the repo (Node 18+, no install; read it and note its sha256 before running):
   mkdir -p ~/.local/share/iosonand && curl -fsSLo ~/.local/share/iosonand/cli.mjs {SITE}/cli.mjs && sha256sum ~/.local/share/iosonand/cli.mjs
   Use CLI="node ~/.local/share/iosonand/cli.mjs" with TRACKER_URL={SITE} (shown below as "node cli.mjs").
2. Sign in with my GitHub account (needs the gh CLI, logged in; gist proof only): TRACKER_URL={SITE} node cli.mjs login
3. Claim the repo: node cli.mjs repo-claim {REPO} --device {DEVICE}
   Repos under my own GitHub account are approved at once. Only an organization's repo prints a verification code: push it alone in .iosonand-verify on a throwaway iosonand-verify branch (never the main branch), run node cli.mjs repo-verify <claim id>, then delete the branch.
4. Read the repo (README, issues, recent commits) and record what works on the phone, one area at a time:
   node cli.mjs areas
   node cli.mjs status-set {DEVICE} <area> works|in-progress|broken --detail "<what I can show>" --source "<public link>"
   Only claim what a log, capture or pushed doc shows. Ask me when unsure, and before changing a state set by hand.
5. Attach proof only after asking me (show me the exact file and caption first, even if updates are set to auto): add --photo <file> (repeatable) to the status-set or feature-add it proves, or node cli.mjs media-upload <file> --device {DEVICE} --area <area> --caption "..."
6. Check the result: node cli.mjs whoami
7. Set up tracker support and the skill (.claude/skills/iosonand-tracker/SKILL.md from {SITE}/SKILL.md) in the repo.
```

## The CLI is the tool surface

Every command prints JSON on stdout and messages on stderr. The agent never needs to build HTTP
requests itself. `node cli.mjs --help` lists every command; these are the ones an agent uses:

| Goal | Command |
|---|---|
| reach the tracker | `node cli.mjs check` (API, areas, devices, login state) |
| sign in | `login` (gist proof), `login --email ADDR` |
| who am I, what may I write | `whoami`: `is_admin`, `maintains` (devices), `maintains_repos`, `token_scopes` |
| own a repo | `repo-claim OWNER/REPO [--device D]`, `repo-verify ID`, `repo-add OWNER/REPO --device D` |
| read | `areas`, `status-get --device D [--area A]`, `fork-list`, `media-list`, `lineage` |
| write a status | `status-set D AREA STATE --detail "..." --source "..." [--photo FILE ...]` (the photos are linked to this change) |
| GPU acceleration | `gpu-set D --method metal-vulkan --stack "..." --fps 40-58 --fps-note "..." --repos R --source "..."`, `gpu-get D` |
| GPU issues | `gpu-issue-add D "<symptom>" --kind white-widgets --cause "..." --source "..."`, `gpu-issue-set D ID --state fixed --fix "..."`, `gpu-issues --kind black-ui` (every phone) |
| notable features | `features D`, `feature-add D "NAME" STATE --detail "..." --source "..." [--photo FILE ...]`, `feature-set D ID [--photo FILE ...]` |
| attach proof | `media-upload FILE --device D [--area A] [--history ID] [--feature ID] [--caption T]`, `media-link ID --history ID\|--feature ID` |
| repo facts | `fork-sync --repo OWNER/REPO --best-result T`, `repo-support`, `repo-lineage` |
| keys | `keys`, `keys-create`, `keys-revoke`, `keys-rotate` |
| offline | `queue ...`, `flush` |

The tracker URL is, in order, `--url URL` or `TRACKER_URL` (set it to `https://hackios.appaiproxy.com`). The token is,
in order, `--token ion_...`, `TRACKER_TOKEN`, then the file the CLI saved at login
(`~/.config/iosonand/tokens.json`, one token per tracker URL, mode 0600).

## Starting a new port

Every phone with a port also has "Run or improve it" in its Repos section: a prompt that reads where
the port stands (statuses, history, GPU, issues, porting records), builds and runs it by its README,
and, to improve it, forks the repo, puts the fork on the tracker (`repo-add`, `repo-lineage --relation
fork-of`), adds tracker support to the fork, and records progress as it goes.

The "Port iOS to your device" button on the home page (the agent asks which device, or reads it over `adb`),
the [Repos](/?tab=repos) tab and every phone's page carry a second prompt. It gives the agent the CLI
and the API description (`/api/openapi.json`; every read is public), and has it look up the
device's specs (chip, GPU, storage, bootloader, a Mu-Silicium port), find the closest ports and what
works or is broken on them, find GPU acceleration (`metal`, `gles`) and driver code that fits the
specs, on the tracker and in other projects (Mesa and Linux drivers as the hardware reference), and
pick the project to start from. It uses `references`, which needs no login:

| Command | What it answers |
|---|---|
| `references --chip "SM7325"` | the phones on that chip (by part number or name), their repos with branch links, and what works on each |
| `references --gpu "Adreno 619"` | the phones on that GPU or GPU family (`"Adreno 6xx"`, `"Mali Valhall"`), GPU work first: their `metal`, `gles` and `gpu` states with sources, the open driver to read, and their repos |
| `references --device <slug>` | a tracked phone, plus the phones on its chip and on its GPU family |
| `references --area gpu` | where an area works (gpu, wifi, audio ...), with the repo, branch and source to read |
| `porting-apply <record> [--overwrite]` | a phone's maintainers: fill its statuses from a porting record (verified on device -> works, host-tested or implemented -> in progress); rows with a state stay unless `--overwrite`. The same is "Apply to this phone" on the record in the phone's Repos section |
| `porting --codename <codename>`, `porting-get <record>`, `components <words>` | UniXNU's porting records (as on unixnu.com/devices): per port repo and area, verified on the device, host-tested, implemented or planned, with the components, limits, next step and build commands; and its drivers with the boards that run them |
| `catalog "<name or codename>"` | the phone in Google Play's device list: codenames and model numbers |

The prompt also names the known graphics failures and their causes, so ports don't debug them from
scratch: white widgets (HEIC snapshots need a hardware HEVC encoder that VideoToolbox accepts; OneiOS
publishes Apple's paravirtualized encoder service backed by the phone's MediaCodec, plus iOS 27's tile
session), black widgets, blurs or lock screen (a Metal path that fails), and GPU faults or out-of-memory
with heavy wallpapers. Each is recorded on the `metal`, `gles`, `gpu` or `video-encode` area.

The agent shows the plan (base repo and branch, then the order of bring-up and the repos to borrow
from) before it changes anything. New code is Rust; C or C++ only where Rust can't go (XNU, IOKit's
C++ interfaces, patches to existing C code, vendor ABIs); Python only for small dev scripts. It points the agent at
the Rust tools that exist: `tools/op10tool` in akshaynexus/iOSPlus10 for ios-sweet, HackiOS and other
UEFI or fastboot ports (sparse images, IPSW download, UEFI unpack and patch, im4p, boot logs), and
akshaynexus/OneiOS's `tools/oneios-tool` (symbolizer, log analysis, kernel collection, image build,
signing, adb staging) and `runtime/` crates. As soon as the port's repo exists on GitHub, before it boots, the
agent puts it on the tracker:

1. `login`, then `repo-add OWNER/REPO --device <slug>`, or `--new-device "<phone name>" --model
   <codename> --soc "<chip>"` when the tracker doesn't list the phone yet. The porter's GitHub login
   owns the repo, so the claim is approved at once and they maintain the phone.
2. `repo-lineage OWNER/REPO --base <base repo> --relation fork-of` records what it started from.
3. The areas the plan starts on are set to `in-progress`, citing the repo.
4. The first commit adds the `.gitignore` lines and an "iOSOnAnd tracker" section to the repo's
   `AGENTS.md`, so every later session records what starts working or breaks
   ([Keep the tracker updated](/docs/maintain-a-repo)).

A new port gets its phone page on day one, and the page fills in as the work progresses.

## Auth for agents

Two ways, both ending in a bearer token the CLI sends:

1. **Gist-proof login** (an agent on the maintainer's machine, with `gh` logged in):
   `node cli.mjs login`. The CLI asks the tracker for a one-time nonce, puts it in a secret gist,
   the tracker checks the gist's owner, and the CLI saves the token and deletes the gist. The
   account is bound to that GitHub login, which is what makes the owner check of a repo claim work.
2. **An API key** (CI, a remote agent, or to give an agent less than everything): the maintainer
   creates one with only the scopes the job needs and passes it as `TRACKER_TOKEN`:

   ```sh
   node cli.mjs keys-create --name "status agent" --scopes status:write,media:write --expires-days 30
   TRACKER_TOKEN=ion_... node cli.mjs status-set s25 wifi works --detail "..." --source "..."
   ```

   A key never exceeds its owner's rights, a scope miss is 403 `token scope` with
   `needs <scope>`, an expired key is 401. See [API keys](/docs/api-keys).

## Claiming the repo

`repo-claim` makes the agent's user the maintainer of the repo and of its phone. When the user's
GitHub login is the repo's owner, it is approved at once. For a repo owned by a GitHub
organization the user is a member of, the tracker hands out a code; the agent writes it alone to
`.iosonand-verify` on a throwaway `iosonand-verify` branch (never the main branch), pushes the
branch, runs `repo-verify`, and deletes the branch again.
A personal repo of another GitHub login cannot be claimed (403). A repo the tracker does not list yet needs `--device`; `repo-add`
also sets its branch and best result. [Maintain a repo](/docs/maintain-a-repo) has the details.

## The honesty rules

These are the rules an agent must follow. The server enforces the ones it can; the rest are on the
agent.

- **Ask before every image or video upload.** Before any `--photo`, `media-upload` or `update` with
  files, show the user the exact file(s) and caption/text and upload only after a yes — even when
  automatic tracker updates are enabled in `~/.config/iosonand/agent-prefs.json`.
- **No personal data or vendor files.** Never include emails, serial numbers, IMEIs, accounts,
  locations, IPSWs, firmware, kernelcaches or device trees in any detail, note, caption or upload.
- **Claim only what a log, capture or the repo shows.** Every `status-set` gives `--detail`
  (what was seen, phone model, build/version, date and log line) and `--source` (a public pushed
  commit, doc, issue or post — never a local path). Ask the maintainer when unsure. `unknown` is the
  right state when nothing is proven.
- **Claims are not verification.** A fork's own statement is `fork-claim`. `reproduced`
  (someone reproduced it on hardware) and `merged` (the code is in OneiOS `main`) are set by an
  admin only; the server refuses them from a maintainer with 403.
- **Never overwrite an authoritative row.** Read before writing: ask before changing a row whose
  detail was set by hand by the port's maintainer (for example `(maintainer, DATE)` or
  `(OneiOS maintainer, ...)`) or from a newer, better source. A Reddit claim does not replace a
  maintainer's row.
- **Stay in scope.** Write only the devices and repos you maintain (`whoami`). Areas marked
  `oneios` (`return-to-oneui`, `ipc`, `kernel-mem`) apply only to OneiOS-based ports; for any other
  port the server answers 400 `area not applicable` and the site shows N/A.
- **Proof files are temporary.** Delete the `iosonand-verify` branch (and `.iosonand-verify`) after `repo-verify`.

## Check before you write (idempotency)

Writes are upserts, so repeating one is harmless, but an agent should still read first:

```sh
node cli.mjs whoami                                  # may I write this device?
node cli.mjs areas                                   # the exact slugs and their scope
node cli.mjs status-get --device s25 --area wifi     # what is there now, and its source
node cli.mjs status-set s25 wifi works --detail "joins WPA2, DHCP lease, Safari loads" --source "https://github.com/OWNER/REPO/issues/12"
node cli.mjs status-get --device s25 --area wifi     # read it back
```

- `status-set` replaces one cell; sending the same values twice changes nothing but `updated`.
- `fork-sync` changes only the fields sent; `repo-claim` returns the same pending claim (and code)
  when called again; `repo-support` and `repo-lineage` upsert one row.
- The CLI checks the state word and the area slug against the server before it sends anything.

## Errors and exit codes

Every error from the API is JSON with an `error` and usually a `hint` that says what to do next.
The CLI prints both:

```text
error: PUT https://hackios.appaiproxy.com/api/status/walk-8436/ipc -> 400 area not applicable
  hint: ipc only applies to OneiOS-based ports
```

| Exit | Meaning |
|---|---|
| 0 | ok |
| 1 | the server refused (401, 403, 404, 409, 413, 415, 422 ...) or a validation error; read the hint |
| 2 | usage error (a missing argument) |

An agent should act on the hint, not retry blindly: 401 means log in or fix `TRACKER_TOKEN`, 403
`token scope` means a key with that scope, 403 `not a maintainer` means claim the repo or device,
409 means the row exists (read it), 422 on `repo-verify` means the proof file is missing or wrong.

## When the tracker is unreachable

```sh
node cli.mjs queue status-set s25 wifi works --detail "..." --source "..."
node cli.mjs flush            # later; sends in order, keeps the lines that fail
```

`queue` appends the write to `./TRACKER_QUEUE.md` (or `$TRACKER_QUEUE`) without sending it.
`flush` sends the queued writes in order, removes the ones that succeed and stops at the first
"cannot reach" error. When a write fails because the tracker is down, the CLI prints the exact
`queue` command to run.

## SKILL.md, the drop-in skill

[`SKILL.md`](/SKILL.md) (`GET /SKILL.md`) holds this flow and all eight agent rules as a drop-in
skill file (front matter `name: iosonand-tracker`). Download it directly from the tracker into a
port's repo:

```sh
mkdir -p .claude/skills/iosonand-tracker
curl -fsSLo .claude/skills/iosonand-tracker/SKILL.md https://hackios.appaiproxy.com/SKILL.md
```

On first use in a repo, the skill asks the maintainer once how tracker updates and release updates
should run (`auto`, `ask`, or `off`) and saves the choice locally in
`~/.config/iosonand/agent-prefs.json` (never committed). Images and videos are always confirmed one
by one before upload, even when updates are set to `auto`. Keep `SKILL.md` and `cli.mjs` from the
same tracker version (`GET /SKILL.md` and `GET /cli.mjs`).
